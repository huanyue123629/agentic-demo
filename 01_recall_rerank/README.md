# Demo 1：历史工单检索 —— 向量召回 + 规则重排

## 它解决什么问题

客服场景里，用户描述故障的用词和历史工单标题几乎不会重合：
用户说"充不进电"，工单标题写的是"充电宝无法充电 指示灯不亮"。
这个 demo 演示怎么用两段式结构把正确答案排到第一位。

## 两段式结构

```
用户提问
   │
   ├─ 阶段 1  召回（recall）
   │     TF-IDF 稀疏向量 + 余弦相似度，取 top-10 候选池
   │     目标：别漏。召回阶段只看字面相似度，快、可解释、零依赖
   │
   └─ 阶段 2  重排（rerank）
         对候选池逐条算 7 路特征，加权融合后取 top-5
         目标：把正确答案顶上去，并由业务规则兜住字面相似的干扰
```

## 重排用到的 7 路特征

| 特征 | 权重 | 为什么需要它 |
| --- | --- | --- |
| `sim` | 0.45 | TF-IDF 余弦相似度，基础分 |
| `title` | 0.16 | 查询实词在**工单标题**上的覆盖率（0.6）＋标题字符二元组相似度（0.4）。标题是人工写的摘要，信号质量最高 |
| `coverage` | 0.13 | 查询实词在正文里的覆盖率。停用词按 0.35 降权而不是丢弃——中文短句里"钱""要"往往是区分度所在 |
| `clause` | 0.12 | **转折从句对齐**。"能给手机充电，但是自己充不进去电"里前半句只是背景、后半句才是故障点，只匹配前半句的工单要被压下去 |
| `bm25` | 0.12 | 关键词命中的强度，和向量相似度互补 |
| `dup` | 0.08 | 同一答案组的重复工单惩罚，保证列表多样性 |
| `cat` / `helpful` | 0.04 / 0.02 | 分类亲和度、历史处理是否被用户认可 |

每一路特征和它的加权贡献都会在界面和 API 里返回，可直接解释"这条为什么排在前面"。

## 怎么跑

```bash
python pipeline.py        # 直接打印评测结果
python ../serving.py      # 起网页界面，看逐条分数的拆解
```

在 demo 根目录下还可以跑 `python probe_rank.py`，对比"纯相似度 / RRF 名次融合 / 当前实现"三种策略。

## 评测口径

- 评测集 20 条查询，**口语化重写、不与工单原句同义**，分易/中/难三档；
- 命中按"答案组（group）"判定：同一个解决方案有多条历史工单时，命中任意一条都算对；
- 指标：Recall@K、MRR、nDCG@K（二值相关性，按组去重）。

## 实测

| 指标 | 仅向量召回 | 召回 + 规则重排 |
| --- | --- | --- |
| Recall@1 | 0.900 | 0.900 |
| Recall@3 | 1.000 | 1.000 |
| MRR | 0.950 | 0.950 |

指标打平的原因写在根目录 README 的"实测结果"里：18/20 条查询在召回阶段就已经对了，
重排没有发挥空间。**这个 demo 的价值在可解释和可调，不在刷指标**——
真正要提升得先换召回阶段。

## 已知失败案例

| 查询 | 期望 | 实际 | 原因 |
| --- | --- | --- | --- |
| 扫地机在地上转圈圈不干活 | T-4001 边刷缠绕原地打转 | T-4002 回不了充电座 | 需要常识才能把"转圈圈"对应到"边刷缠绕"，词汇级规则无解 |

这类查询就是引入向量模型 / LLM 重排的动机。
