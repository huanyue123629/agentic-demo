# 智能服务赛道 · 两个极简 demo

面向 Anker 黑客松**智能服务赛道**（AI 客服 Agent + 交互前端）的两个可运行小 demo。
纯 Python 标准库实现，**不需要 pip install 任何东西**，clone 下来就能跑。

| demo | 做什么 | 对应方案里的哪句话 |
| --- | --- | --- |
| `01_recall_rerank/` | 历史工单检索：TF-IDF 向量召回 + 规则重排 | "把文本向量化后用相似度做召回，再叠一层规则和加权打分做重排" |
| `02_intent_classifier/` | 客服意图分类：逻辑回归 vs 轻量 MLP vs 关键词 baseline | "给客服问答做意图分类，用逻辑回归和轻量模型跑对比实验" |

## 快速开始

```bash
cd demo
python serving.py
# 浏览器打开 http://127.0.0.1:8000
```

Windows 下也可以直接双击 `start-demo.cmd`（默认 8000 端口，可传参换端口）。
两个 `.cmd` 脚本刻意只用 ASCII 字符：cmd.exe 按控制台码页解析 `.cmd` 文件，
在里面写中文在 zh-CN 系统上会变成乱码导致命令解析失败。

页面分三个标签：① 召回 + 重排的逐条分数拆解、② 三个模型的意图预测对比、
③ 两个任务的离线评测指标。换端口：`DEMO_PORT=8125 python serving.py`
（Windows PowerShell 用 `$env:DEMO_PORT=8125`）。

## 实测结果

### Demo 1：检索排序（20 条评测查询，命中按"答案组"判定）

| 指标 | 仅向量召回 | 召回 + 规则重排 |
| --- | --- | --- |
| Recall@1 | 0.900 | 0.900 |
| Recall@3 | 1.000 | 1.000 |
| MRR | 0.950 | 0.950 |

**怎么解读**：这次重排没有提升指标，原因值得说清楚——评测集 20 条查询里有 18 条
在召回阶段就已经把正确答案排在第 1 位了，重排只能在剩下的噪声里做微调，
天花板效应导致指标打平。重排真正的价值在于**可解释性和可控性**：
每一分都能拆成"相似度 / BM25 / 词覆盖 / 标题命中 / 分类亲和 / 历史质量 / 转折对齐"，
运营可以直接调权重，而不需要重训模型。要真正提升指标，得先换掉召回阶段
（向量模型或双塔召回），再让重排做精排——这是下一步的事，不是靠调参能解决的。

仍然答错的查询（`/api/retrieval/eval` 的 `failed_queries`）：

- "扫地机在地上转圈圈不干活" → 期望 T-4001（边刷缠绕原地打转），实际排到 T-4002（回不了充电座）

这类查询需要常识才能把"转圈圈不干活"对应到"边刷缠绕"，是纯词汇级规则的硬边界，
也是引入向量模型或 LLM 重排最有说服力的场景。

### Demo 2：意图分类（8 类客服意图）

训练集 430 条（112 条手写 + 同义替换/口语前缀扩增），留出集 16 条**手写且未参与训练**。

| 模型 | 留出集 accuracy | 95% 置信区间 | macro-F1 |
| --- | --- | --- | --- |
| 关键词打分（baseline） | 0.813 | 0.570 ~ 0.930 | — |
| 逻辑回归 + TF-IDF | **0.938** | 0.718 ~ 0.988 | — |
| 轻量 MLP（1 隐层，16 维） | **0.938** | 0.718 ~ 0.988 | — |
| 4 折交叉验证（未扩增手写数据） | 逻辑回归 0.672 ± 0.064 / MLP 0.589 ± 0.053 | | |

（表里的数字由 `python api_test.py` 或页面上「训练并查看指标」实时算出，不再是硬编码的。）

**三个结论**：

1. **有训练的模型明显强于关键词规则**（0.94 vs 0.81），说明意图分类值得上模型；
2. **轻量 MLP 打平逻辑回归**，加非线性没有收益 —— 在这个数据规模下，
   瓶颈是样本量而不是模型容量，直接上 BERT 的边际收益有限；
3. **4 折交叉验证的波动（±0.06）比模型间的差距还大**，
   所以留出集上的 0.94 不能过度解读 —— 页面上同时给出 Wilson 95% 区间就是这个原因。

> 关于"轻量 BERT"：环境里不一定有 `transformers`/`torch`（本 demo 刻意不装），
> 所以代码里用 `MLP` 作为轻量模型代理，并提供了 `transformer_available()` 探针，
> 装了依赖再换成 BERT 微调即可，评测代码不用改。

## 工程上值得一提的三个点

1. **稀疏特征而不是稠密矩阵**。中文 TF-IDF 词表约 1600 维，但一句话只有几十个非零项。
   第一版用稠密 `list[float]` 跑 MLP，一个 epoch 要几十秒（2000×64 的全矩阵乘法）；
   改成 `dict{下标: 权重}` + 稀疏梯度后，同样的训练几秒跑完，指标不变。
2. **评测集不能和训练集同分布**。检索的评测查询如果直接改写工单原句，
   两条路都会满分，评测就失去意义；意图分类的测试集如果是模板批量生成的，
   准确率会假高到 0.99。这里的检索查询是口语化重写的，意图测试集全部手写。
3. **置信度兜底**。`/api/classify` 除了给意图，还会按置信度和与第二名的差值
   给出"自动答复 / 坐席确认 / 转人工"的建议——真实客服系统里这个兜底比准确率更重要。

## 已知限制（写在前面，避免被当成 bug）

- 语料是**人工构造的小样本**（20 条工单、8 类意图），指标只用于验证流程跑得通，
  不能当作生产环境的准确率预期；
- 分词在没有 jieba 时退化为字符 1-2 gram，效果略差但行为可复现；
- 重排权重是在这份小评测集上人工调出来的，换到真实数据需要重新标定；
- 界面是原生 JS 单文件，没有做响应式适配和浏览器兼容性处理。
